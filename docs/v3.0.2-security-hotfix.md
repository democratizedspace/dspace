## Source evidence

The base Dockerfile uses `node:20-bookworm-slim`; its final runtime inherits that
base. The [image vendor's immutable Dockerfile](https://github.com/nodejs/docker-node/blob/8e93bb03443b68eccbddc0f1e31a5e9756f7e70e/20/bookworm-slim/Dockerfile)
installs upstream Node tarballs into `/usr/local`. It is not Debian's nodejs package.
Distribution Brotli backports therefore do not establish a fix for this runtime.
The [October 21 Node advisory](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)
includes CVE-2026-111497 and fixes supported lines including 24.22.1; EOL Node 20
has no fix in that release. Source exposure does not prove a current deployment,
attacker reachability, exploitation, downtime, or compromise.

## Review and owner rollout gates

1. Keep the PR draft until independent review, applicable AI feedback, and all
   required CI checks pass on the exact final head. Run the existing lint, type,
   build, unit, E2E and image smoke checks plus `node scripts/check-node-runtime.mjs`.
2. Before any publication, the release owner must choose and review a publication
   path for the maintenance branch. Its historical workflows have legacy semantic
   tag publication behavior; do not dispatch them or create tags as a shortcut.
   Record the reviewed source SHA, immutable image digest, architecture manifests,
   and evidence that the final image contains Node 24.22.1. Verify the source diff
   from the v3.0.1 commit contains only this approved hotfix, not v3.1.x content.
3. Before staging, record the exact cluster context, namespace, Helm release,
   current image digest/source, approved target digest and rollback procedure.
   Stop on any mismatch or missing environment identity. Select a separately
   approved compatible chart; do not reuse tombstoned chart 3.0.1 for publication.
4. The owner deploys the immutable hotfix image to **staging first**. Verify the
   deployed digest and full source SHA, application 3.0.2, final Node runtime and
   health endpoints; smoke `/quests`, `/processes`, `/docs`, `/settings`, save
   loading and the existing chat path. Run the approved regression suite without
   exploit payloads. Record results and approval before production promotion.
5. Capture fresh production identity and rollback evidence, then promote the
   **same tested digest** to production. Recheck environment guards, runtime,
   artifact identity, health and functional smoke. Roll back to the freshly
   recorded prior digest if verification fails; record that it may retain this
   security exposure. The P0 remains open until production verification succeeds.
