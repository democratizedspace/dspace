## Source evidence

The base Dockerfile uses `node:20-bookworm-slim`; its final runtime inherits that
base. The [image vendor's immutable Dockerfile](https://github.com/nodejs/docker-node/blob/8e93bb03443b68eccbddc0f1e31a5e9756f7e70e/20/bookworm-slim/Dockerfile)
installs upstream Node tarballs into `/usr/local`. It is not Debian's nodejs package.
Distribution Brotli backports therefore do not establish a fix for this runtime.
The [October 21 Node advisory](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)
includes CVE-2026-111497 and fixes supported lines including 24.22.1; EOL Node 20
has no fix in that release. Source exposure does not prove a current deployment,
attacker reachability, exploitation, downtime, or compromise.

## Review and owner rollout gates

1. Mark the approved PR ready to trigger repository AI reviews; hand off for human
   review only after independent review, applicable AI feedback, and all
   required CI checks pass on the exact final head. Run the existing lint, type,
   build, unit, E2E and image smoke checks plus `node scripts/check-node-runtime.mjs`.
2. Before any publication, the release owner must choose and review a publication
   path for the maintenance branch. Do not dispatch historical `ci-image.yml`:
   its manual input selects main/v3, it publishes mutable/semantic aliases, and
   it is not the approved maintenance publication path. `build.yml` no longer
   builds or publishes on release tags, so the post-cutover tag cannot rebuild
   the deployed image. Neither maintenance-branch pushes nor this PR publish.
   Record the reviewed source SHA, immutable image digest, architecture manifests,
   and evidence that the final image contains Node 24.22.1. Verify the source diff
   from the v3.0.1 commit contains only this approved hotfix, not v3.1.x content.
3. Before staging, record the exact cluster context, namespace, Helm release,
   current image digest/source, approved target digest and rollback procedure.
   Stop on any mismatch or missing environment identity. Select a separately
   approved compatible chart; do not reuse tombstoned chart 3.0.1 for publication.
4. The owner deploys the immutable hotfix image to **staging first**. Verify the
   deployed digest and full source SHA, application 3.0.2, final Node runtime and
   health endpoints; smoke `/quests`, `/processes`, `/docs`, `/settings`, save
   loading and the existing chat path. Run the approved regression suite without
   exploit payloads. Record results and approval before production promotion.
5. Capture fresh production identity and rollback evidence, then promote the
   **same tested digest** to production. Recheck environment guards, runtime,
   artifact identity, health and functional smoke. Roll back to the freshly
   recorded prior digest if verification fails; record that it may retain this
   security exposure. The P0 remains open until production verification succeeds.
6. Only after successful production cutover, the owner verifies that production's
   recorded source SHA equals the reviewed commit and that remote Git tag
   `v3.0.2` is authoritatively absent. Create an annotated `v3.0.2` tag at that
   exact commit and push only that tag. Stop if a tag already exists at a different
   commit or if absence cannot be verified. Record the tag object, peeled source
   SHA, deployed image digest and production receipt together. No tag is created
   during source preparation, image publication or staging. Update release history
   and remove the addendum's pending label only through owner-approved follow-up.

## Owner publication before the Git tag

The release tag is a post-cutover record, not an input to the image build. A
separately approved owner publication can use the existing Docker Buildx tooling:

1. Use a clean checkout of the full reviewed commit SHA, descended from
   `1a31a569aff2dbeb238e8c2688b9e85140d2077d`. Verify its diff contains only the
   approved hotfix and root/frontend versions are 3.0.2. Do not build main or
   substitute a branch name that may move. Record the exact source SHA.
2. Use one new image tag derived from that full SHA, for example
   `ghcr.io/democratizedspace/dspace:hotfix-<full-reviewed-sha>`. Verify the registry
   coordinate is authoritatively absent; authentication/network failures do not
   mean absent. Stop rather than overwrite any existing coordinate.
3. Build and publish only that coordinate from the clean checkout for
   `linux/amd64,linux/arm64`, using the root Dockerfile, with `GIT_SHA` and
   `VITE_GIT_SHA` both set to the verified full SHA, `ENFORCE_VITE_GIT_SHA=1`, and
   `DSPACE_VERSION=v3.0.2+<short-sha>`. Set explicit OCI image labels with Buildx
   `--label`: `org.opencontainers.image.revision=<full-reviewed-sha>`,
   `org.opencontainers.image.source=https://github.com/democratizedspace/dspace`,
   and `org.opencontainers.image.version=v3.0.2+<short-sha>`.
   Record Buildx metadata and independently
   resolve the registry index and per-platform digests. Do not publish `latest`,
   `v3.0.2`, or other semantic image aliases as part of this handoff.
4. Validate the published artifact's source labels, baked build identity, final
   Node 24.22.1 runtime and application smoke behavior. Use the resulting exact
   `tag@sha256:...` image reference for staging and production without rebuilding.
   These are owner-run steps requiring publication approval; this PR executes none.
