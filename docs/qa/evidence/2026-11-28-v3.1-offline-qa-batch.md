## Relay and request privacy

The browser passed a raw PEM from the stub selection response through the
production client, sent the normalized key representation in the dispatch,
and completed an encrypted request/response. The disposable compute fixture
used only the client's public key to encrypt the response. In the actual
browser entry point no client key pair is injected; the relay attempt
generates it locally and uses the private half for response decryption.
The exact dispatch and subsequent request schemas contain only the public
key and protocol ciphertext/proof fields, not the client private key.

The direct fixture recorded all provider requests, enforced the exact
select/dispatch/retrieve/acknowledge sequence and verified the absence of
authorization and cookies. The separate token.place client test rejects
synthetic credential, authorization, secret, inventory and raw-save
sentinels supplied through optional request metadata. Scoped retrieval,
cancellation and acknowledgement proofs are protocol fields, not a
token.place account credential. This evidence does not qualify relay-owned
logs, state or live provider compatibility, nor the policy for echoed
response metadata.

## Stored OpenAI key and opt-in

Chromium saved a synthetic key locally through Settings, selected token.place,
reloaded, then selected OpenAI and completed a stubbed turn using the
previously saved key without reentering it. All provider network activity was
blocked in this fixture and the mock only returned the success reply for the
exact expected key. The Settings flow separately verified persistence in the
existing browser state field, reload, and clearing. The key remains local
until an explicit OpenAI call, where an actual user-supplied key is used with
OpenAI, not token.place or DSPACE's proxy. This does not establish broad
backward compatibility: a synthetic localStorage-only state without
matching durable credential state did not authorize submission. That box
remains open, and no credential gate was changed.
