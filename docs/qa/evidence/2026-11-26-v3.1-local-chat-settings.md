# v3.1.0 local Chat and Settings browser evidence

On 2026-11-26 UTC, Playwright 1.54.2 and its pinned Chromium Headless Shell
139.0.7258.5 (build 1181) exercised a local Astro preview using Node 24.22.3,
with token.place as the deployment default. The application source was
`ce6e3a1f297965b67978c731b1117b9d91bc2cd6`. The exercised app code is unchanged
by the accompanying browser-test and checklist changes.

With the lockfile dependencies and Playwright browser installed, the focused
repository commands are:

```bash
npm run build:meta
npm run build:docs-rag
cd frontend
ASTRO_TELEMETRY_DISABLED=1 DSPACE_ENV=dev DSPACE_DEFAULT_CHAT_PROVIDER=token-place \
  PLAYWRIGHT_PORT=4189 PW_WORKERS=2 \
  npx playwright test e2e/chat-provider-routing.spec.ts \
    e2e/token-place-chat-banners.spec.ts e2e/settings-page.spec.ts \
    e2e/chat-message-flow.spec.ts --project=chromium
```

Result: **42 passed**, **2 skipped**. The skipped cases explicitly require a separate
OpenAI-default deployment fixture; this run used the token.place default. Both
passed in a separate preview run with `DSPACE_DEFAULT_CHAT_PROVIDER=openai`
and the provider-routing spec filtered by `--grep "OpenAI deployment default"`.

## Locally verified behaviors

- A clean browser context and client-state purge preceded the fresh Chat flow.
  The hydrated Chat panel identified token.place as the default, did not display
  an OpenAI key prompt, and rendered a reply from the mocked relay.
- Settings defaulted to token.place without a credential field. Choosing OpenAI
  changed Chat's provider. Saving and clearing a deliberately invalid credential
  updated Settings and local storage without attempting a provider request. The
  explicitly saved OpenAI selection survived reload; switching back to token.place
  persisted across reloads of both Settings and Chat. OpenAI Chat without a key
  showed Settings guidance and made no provider request.
- Mocked token.place failures exercise an unreachable relay, actual HTTP 400,
  429 and 503 at dispatch, a successful HTTP response with malformed encrypted
  completion content, and a synthetic aborted fetch (not a measured timeout). OpenAI authentication and rate or quota errors
  exercise the browser client's SDK fixture. The tests confirm understandable
  UI banners, omit the synthetic provider diagnostic from the Chat panel for
  the injected diagnostic cases, and leave the Send control usable.

## Limits

The local verification blocked live provider traffic and used synthetic
credentials and responses. It does not verify service health, staging or
production deployment, browser compatibility outside Chromium, actual credential
validity, or absence of provider diagnostic text from logs. The live staging,
promotion and rollback checks remain open.
