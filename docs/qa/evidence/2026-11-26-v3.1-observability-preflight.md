## Offline evidence (2026-11-26 UTC)

On DSPACE main base `ce6e3a1f297965b67978c731b1117b9d91bc2cd6` with the
test change in this PR, Node 24.22.3 and Helm 3.12.3 ran these checks locally:

```sh
npm run build:meta
node scripts/run-vitest.mjs run --config vitest.config.mts --testTimeout 20000 --maxWorkers=1 \
  tests/metricsProcessRuntime.test.ts tests/metricsEndpoint.test.ts \
  tests/helmChartMetrics.test.ts tests/metricsFallback.test.ts
```

All 21 tests passed. The endpoint test used the real server-side `prom-client`
registry. With metrics enabled and a synthetic token configured, the request
without authentication returned `401`. The authenticated scrape returned real,
non-negative CPU, resident-memory, Node heap, and event-loop lag samples without
client-supplied labels or the token. Temporarily omitting default metric
registration made the new test fail on the missing CPU sample; the production
source was restored before the passing run. The canonical chart renders the authenticated
ServiceMonitor and expected labels only when requested; enabling metrics without
a Secret reference fails rendering. An ingress with no dedicated metrics rule
does **not** establish that the public catch-all route blocks the metrics path.
Nothing here verifies deployed behavior, assembled dashboards, alert delivery,
or coverage of runtime configuration values in a published candidate.

## Capture one immutable staging candidate

This is a plan, not an executed drill or an approval to deploy. Use it after the
release owner has deployed the selected staging candidate. Keep staging results
with the matching [v3.1 checklist](../v3.1.md#115-required-staging-evidence).

1. **Record identity and stop on mismatch.** Record UTC start/end, environment,
   cluster, namespace, release, finalized approval reference, full source SHA,
   deployed immutable image tag and digest, chart version and digest, and values
   revision. Attach the previous known-good image digest and chart/values
   reference as the rollback target. Check that approved and running identities
   match every ready replica, including pod image IDs and `dspace_build_info`;
   compare each architecture to the approved platform manifest where applicable.
   Missing, stale, ambiguous, or mixed identity stops evidence collection. A
   mutable tag or the old approved-release series is not sufficient.
2. **Verify discovery and isolation.** From approved in-cluster tooling, verify
   the loaded ServiceMonitor selects exactly the candidate deployment and all
   expected ready targets are `up`. Verify the public application URL does not
   serve metrics to an unauthenticated request; also verify that monitoring
   interfaces are not publicly exposed. Record status and target labels, never
   an authentication header, a Secret, or a public response body. A working
   internal scrape does not substitute for the unauthenticated public check.
3. **Exercise the candidate and collect bounded aggregates.** Use controlled,
   non-personal staging traffic and record the provider and whether the optional
   relay proxy was enabled. Confirm real provider completion in the browser
   independently of an intercepted smoke or a server-observed success. During a
   recorded UTC query window, scope application PromQL to the candidate's loaded
   cluster, environment, namespace, release, and app labels; tie Kubernetes
   metrics to the candidate pods. Capture availability/rate, HTTP 5xx ratio,
   latency, process/runtime samples, dChat and dependency outcomes where
   applicable, pod readiness/restarts/resources, and release identity. Verify
   the loaded dashboard query for the candidate provider uses metric label
   `tokenplace` (runtime configuration value `token-place`). Keep its UID and a
   sanitized export or screenshots. No data, no eligible requests, a zero
   denominator, or telemetry from another release does not pass a gate. If an
   optional disabled path cannot produce a signal, document the gap for the
   release owner rather than marking it verified.
4. **Verify alert mapping and recovery.** Reconcile the six release alert
   categories in [section 11.4](../v3.1.md#114-release-blocking-dashboard-and-alerts)
   to installed rules, expressions, provisional thresholds, evaluation duration,
   environment labels, and receivers. For one owner-approved, staging-only
   controlled alert test, record the trigger, expected alert, actual firing and
   delivered notification or Prometheus evidence, mitigation, and recovery to
   inactive. Do not widen routing or disrupt production. A loaded rule or
   notification route alone is not delivered-alert evidence. Record any missing
   rules or producer signals as outstanding Sugarkube work.
5. **Close the evidence window.** Review metrics label names and relevant log
   field names for privacy. Save only sanitized aggregate results and identity
   references; do not attach raw logs, chat contents, headers, keys, credentials,
   or correlation tokens. Record the soak interval, traffic and baseline, and
   where to find the known-good rollback coordinates. Leave each live checkbox
   open until the corresponding evidence is attached. Any subsequent candidate
   change invalidates the affected evidence and requires revalidation.
