## Evidence and limits

- [Settings](../../../frontend/e2e/settings-page.spec.ts): select the provider
  opposite the initial choice and read the saved provider directly from the
  application's IndexedDB record. Remove the localStorage mirror before app
  startup on both reload and Chat navigation, then confirm the chosen radio
  and hydrated Chat provider. This distinguishes the primary store from the
  separately tested fallback. The synthetic Settings flow also checks that
  token.place presents no credential input when selected.
- [Provider routing](../../../frontend/e2e/chat-provider-routing.spec.ts):
  select Hydro and confirm the synopsis and portrait. Submit a quest-related
  question from fresh Chat and confirm the rendered fixture response and the
  exact question inside the decoded compute request. The fresh token.place
  panel presents no credential prompt. Saving a synthetic OpenAI key is limited
  to explicitly selecting the OpenAI option in the local test.
- [Chat context](../../../frontend/e2e/chat-rag-context.spec.ts): the local
  OpenAI opt-in fixture supplies a game save with a quest, an active process
  and a sample inventory item. The test captures the outgoing shared prompt
  and checks the corresponding quest progress, active process and inventory
  summaries. A fixed browser clock makes the active process precisely 15
  minutes into a one-hour run. The captured prompt must include the process
  title followed by `in progress (25%)`; a missing or wrong percentage fails.
  This is a test of shared prompt assembly, not a live model test.

Provider calls are mocked or blocked. These results neither qualify an
immutable candidate nor establish live relay, metrics, rollback, or production
behavior. The staging and promotion gates remain open.
